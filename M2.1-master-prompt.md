## Scope

Restructure `server/` into the module layout defined in `docs/02-architecture-api.md` §2.1, and stand up infrastructure only. No feature logic, no auth logic, no AI logic in this phase.

## Tasks

1. Create the folder structure:
   ```
   server/src/
   ├── config/        (db.js, env.js — ai.js and storage.js are stubs for now, filled in M5/M6)
   ├── modules/        (empty folders: auth/, users/, resumes/, interviews/, analytics/ — no files yet)
   ├── ai/              (empty — filled in M5)
   ├── middleware/     (error.js, rateLimit.js — auth.js and upload.js are stubs, filled in M3/M6)
   ├── utils/
   ├── app.js
   └── server.js
   ```

2. Move `config/db.js` (existing, working Mongoose connection + fail-fast pattern) into `src/config/db.js` unchanged — it's already correct.

3. Create `src/config/env.js` — centralized environment variable loading, with **phased requirement**, not all-at-once:

   **Required for M2.1 startup** (missing any of these fails fast with a clear error):
   - `MONGO_URI`
   - `PORT`
   - `CLIENT_ORIGIN`

   **Declared now, but NOT required until their module is implemented:**
   - `JWT_ACCESS_SECRET` → required starting M3
   - `GEMINI_API_KEY` → required starting M5
   - `SUPABASE_URL` → required starting M6
   - `SUPABASE_KEY` → required starting M6

   `env.js` should still read/expose these future-phase vars (so later phases have a stable import), but must NOT block M2.1 startup if they're unset. When a future module actually starts using one, that module's own config layer is responsible for failing clearly if its variable is missing — not `env.js` globally today. Do not make foundation depend on secrets three phases away.

4. Create `.env.example` at `server/` root:
   ```env
   # Backend
   PORT=5000
   MONGO_URI=your_mongodb_connection_string
   CLIENT_ORIGIN=http://localhost:5173

   # Authentication - required from M3 onward
   JWT_ACCESS_SECRET=your_secret_here

   # AI - required from M5 onward
   GEMINI_API_KEY=your_gemini_api_key

   # Storage - required from M6 onward
   SUPABASE_URL=your_supabase_project_url
   SUPABASE_KEY=your_supabase_service_key
   ```
   The comments making the phase dependency explicit are required, not optional — this is what keeps the timeline legible to whoever configures the repo next.

5. Split `server.js` into:
   - `src/app.js` — Express app setup: CORS (allowlist from `CLIENT_ORIGIN`, not `*`), JSON body parsing, mounts a versioned router at `/api/v1` (empty for now — modules mount their own routers here starting M3), health-check route at `GET /`.
   - `src/server.js` — imports `app.js`, connects DB via `config/db.js`, starts listening only after DB connects (keep the existing fail-fast instinct from the current `server.js`).

6. `src/middleware/error.js` — single error-handling middleware, consistent shape from `docs/02-architecture-api.md` §3:
   ```json
   { "error": { "code": "...", "message": "...", "details": {} } }
   ```
   Mount last in `app.js`. Never leak stack traces to the client in any environment — log full details server-side only.

7. `src/middleware/rateLimit.js` — general IP-based limiter from `docs/06-security.md` §0.1 (applies to all routes). Stub a named export `aiRateLimit` as a no-op passthrough for now — filled in M5.

8. Do NOT touch the existing auth files — see guardrail #6. They move and get refactored in M3.
